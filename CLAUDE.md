# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev       # Vite dev server at http://localhost:5173 (client-only, localStorage mode)
npm run backend   # Express API at http://localhost:10000 (server.js) — Vite proxies /api to it in dev
npm run build     # prebuild runs scripts/generate-seo-files.mjs, then vite build to /dist
npm run preview   # preview the production build
npm run lint      # eslint .
```

There is no test suite; CI (`.github/workflows/ci.yml`) only runs `npm run lint` and `npm run build` on push/PR to `main`.

To run the full backend locally, copy `.env.example` to `.env` and set `DATABASE_URL` (Postgres), `JWT_SECRET`, and optionally `APP_ENCRYPTION_KEY` (only needed to configure school SSO — those endpoints return 503 without it) plus SMTP vars (`EMAIL_HOST`/`EMAIL_PORT`/`EMAIL_USER`/`EMAIL_PASSWORD`) — without SMTP config, recovery codes are shown in the UI instead of emailed. Without `DATABASE_URL`, the backend runs in email-only mode (no accounts API).

## Architecture

This app has two parallel, loosely-coupled data layers, and most nontrivial changes touch the boundary between them:

1. **Client-only mode (default)**: all state lives in `localStorage` under the `voluntrack:` namespace (`voluntrack:user`, `voluntrack:logs`, `voluntrack:goals`, `voluntrack:achievements`, `voluntrack:theme`). `src/api/index.js` is the data-access layer over localStorage; `src/lib/storage.js` defines the read/write rules and `src/lib/achievements.js` defines badge-earning logic. The app is fully usable with no backend running.
2. **Server-backed mode (optional)**: when `DATABASE_URL` is set, `server.js` boots a Postgres-backed Express API for accounts, school/organization dashboards, public volunteer tasks, and review moderation. `server/db.js` owns the schema and connection — beyond the core `users`/`schools`/`logs`/`goals` tables, it also covers `organizations` (multi-school orgs), `public_tasks`/`public_task_signups` (with attendance tracking), `supervisor_verifications` (hour-verification workflow), `parent_child_links`, `school_invites`/`organization_invites`, `contact_messages`, and `reviews` (moderation queue for the public testimonials on `About.jsx`); most migrations are additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements run on boot rather than a migration tool. `server/auth.js` handles JWT signing/verification and bcrypt password hashing; `server/routes/{auth,authSso,school,organization,logs,parent,contact,reviews,invoices,settings,status,storage}.js` are the route handlers (mount order is in `server.js` — `/api/auth/sso` must stay ahead of `/api/auth`); `server/ids.js` generates IDs/tokens.

`src/lib/logSync.js` bridges the two: logs authored locally can sync to the server side. When editing sync logic, check both the localStorage shape (`storage.js`) and the Postgres schema (`db.js`) stay compatible — this is not enforced by types.

Request-handling flow, middleware order, and the auth-gating pattern for `server/` are in `server/CLAUDE.md`.

### Roles

Seven roles gate routes and dashboards: `student`, `volunteer`, `parent`, `school`, `school_staff`, `org`, `admin` (see `users_role_check` constraints in `server/db.js` and `requireAuth(...)` calls in `server/routes/*.js`). `organizations` can own multiple `schools` (`schools.organization_id`); `org` accounts manage their schools' invites, `school`/`school_staff` manage their own students/staff, `parent` accounts link to student accounts via `parent_child_links`, and `admin` has cross-cutting access (school/org approval, payment status, review moderation, contact-message replies).

Dashboard tabs have their own addresses (#579), like `/status/:tab` and `/admin/:tab`: `/school/dashboard/:tab?/:sub?` (reports [documents|hours], students [list|progress|graduation|add], volunteer, setup [staff|requirements|sso|domain|branding|billing], messages) and `/organization/dashboard/:tab?` (hours, requirements, announcements, invites). `src/lib/dashboardTabs.js` maps between the address and each dashboard's tab state; the first tidy-up of the address replaces it, every tab picked after that is pushed, so Back steps through tabs. Emails can link straight to a tab. Which pages each role may open is one table, `ROUTE_ROLES` in `src/lib/roleAccess.js`, passed to `<Protected roles>` in `src/App.jsx`; admin opens every page, and a blocked page sends the account to its own home. Keep `Sidebar.jsx` / `MobileTabBar.jsx` in step with it, and draw links to other roles' pages with `canOpen()` (Dashboard's `RoleLink`) so they don't bounce.

### Notable conventions

- Path alias `@` → `src/` (configured in `vite.config.js` and `jsconfig.json`).
- Dark is the default theme (`useTheme.js` falls back to `'dark'`); a device's choice persists at `voluntrack:theme`.
- **Text size, high contrast and easy-read font** (`src/hooks/useDisplayPrefs.js`, `AccessibilitySettings` in Settings and under the Login/AppWelcome language picker): device-only, at `voluntrack:text-size` / `voluntrack:contrast` / `voluntrack:font`, applied as `data-text-size` / `data-contrast` / `data-font` on `<html>` before first paint by `public/display-prefs.js` (a file, not inline, because the CSP allows only `'self'` scripts; the prerendered pages need it) — keep it in step with the hook. Text size scales the root font, so use rem (`text-[0.625rem]`, not `text-[10px]`) for anything that should grow. The easy-read font (#553) is Atkinson Hyperlegible, self-hosted in `public/fonts/` (SIL OFL) and left out of the service-worker precache, so only people who turn it on download it. High contrast remaps the muted/status colour utilities in `src/index.css` through `--hc-*` variables chosen per surface (dark by default, light on light surfaces), so a new component gets it without its own CSS.
- Drag-and-drop proof uploads are read via `FileReader` and stored as base64 in localStorage — keep proof files under ~1MB, since this inflates localStorage.
- Backend security posture (see `SECURITY.md`): rate limiting, input validation, parameterized Postgres queries via `pg`. Preserve parameterized queries when touching `server/db.js` or route handlers — no string-concatenated SQL.
- `server/turnstile.js` (`verifyTurnstile()` middleware) guards the public unauthenticated write endpoints (`POST /api/contact`, `POST /api/auth/register/send-code` — not `/register` itself, which needs the code that request emailed — `POST /api/{school,organization}/register`) and the two sign-in endpoints a bot can guess against (`POST /api/auth/login`, and `POST /api/auth/sync-login`, where a 5-digit PIN with no email is the whole credential — its QR-scan paths on `SyncLogin.jsx` spend a token too) with Cloudflare Turnstile; the client widget is `src/components/Turnstile.jsx` (config in `src/lib/turnstile.js`). Both are no-ops unless `TURNSTILE_SECRET_KEY` / `VITE_TURNSTILE_SITE_KEY` are set — if you add the check to a new endpoint, wire the widget into its form in the same change so the two stay in sync.
- **School SSO** (`server/routes/authSso.js`): a school configures an OIDC connection to its own IdP (Google Workspace, Microsoft Entra, or generic OIDC) from the Sign-in tab of `SchoolDashboard`, and its students sign in there instead of with a VolunTrack password. The login page routes by email domain (`GET /api/auth/sso/discover`), the callback hands the SPA a single-use 60s code that `POST /api/auth/sso/exchange` trades for the normal app JWT — `signToken()` is reused, so nothing downstream of login is SSO-aware. Client secrets are AES-256-GCM encrypted via `server/secrets.js` (`APP_ENCRYPTION_KEY`); a connection may only provision accounts for a domain it has proven it controls (Google's `hd` / Entra's `tid` claim, or a DNS TXT record for generic OIDC), and enabling requires a passing test round trip plus a verified domain. `users.password_hash` is nullable because SSO users have none.
- **Audit trail** (`server/audit.js`, `server/routes/audit.js`): `audit_events` is an append-only record of *access* to student data, not just changes. Call `recordAudit(req, {...})` and **do not await it** — it is fire-and-forget by design, so a failed audit insert logs loudly but can never turn a legitimate read into a 500. Actions come from the `AUDIT` constant (a closed set, so a typo can't create a category nobody queries). Never put a credential in `meta` — notably not a presigned URL, which is itself a live grant. Nothing may UPDATE or DELETE a row except the retention prune (`POST /api/audit/internal/prune`, `x-cron-key` vs `CRON_SECRET`, driven by `.github/workflows/audit-prune.yml`), which deletes by age alone; the window is `AUDIT_RETENTION_DAYS` (default 400). Actor FKs are `ON DELETE SET NULL` so deleting an account can't erase what it did — `actor_role` and `actor_hash` survive, keeping events attributable without retaining the identity. Any new route that reads a student's documents or roster must record an event. See #146.
- **Tenant storage** (`server/routes/storage.js`, `server/storage/s3.js`): a school or org attaches its own S3-compatible bucket (`tenant_storage`) so proof-of-service files upload straight from the student's browser to *their* bucket — VolunTrack stores a pointer, never the bytes, so we don't hold minors' documents. Credentials are AES-256-GCM encrypted via `server/secrets.js`, so these endpoints return 503 without `APP_ENCRYPTION_KEY` (same posture as SSO). A config only reaches `status='active'` after `POST /api/storage/test` completes a real put/get/delete round trip, mirroring the SSO "must pass a test before enabling" gate. `server/storage/s3.js` is a hand-rolled SigV4 *query* presigner (no AWS SDK) verified against AWS's published test vector — if you touch the signing math, re-check it against that vector. The tenant-supplied `endpoint` is fetched by our server during a test, so `assertSafeEndpoint()` guards SSRF (https only, no IP literals, no internal names) — keep that check if you add providers. Uploads go browser → bucket via `POST /api/storage/upload-url`: the server picks the object key (never the client's filename) under `students/<userId>/`, and signs `content-length` so an upload is pinned to the size it declared. `logs.proof_storage_id`/`proof_key` are the pointer; `proof_storage_id` is recorded per file rather than resolved from the student's school at read time, so a transfer or bucket rotation can't orphan history. When a log claims a `proofKey`, `keyBelongsTo()` re-verifies it sits in that student's own namespace — never trust a caller-supplied key. `GET /api/storage/download-url/:logId` is the audited moment (`proof.download_url_minted`): after it, the URL works for whoever holds it. See #143.
- **Signed transcripts** (`server/transcript.js`, `server/routes/transcript.js`, `src/lib/transcript.js`, public page `/verify-transcript`): a student exports their server-side logs as a JSON document signed with Ed25519 (`TRANSCRIPT_SIGNING_KEY`; export/import return 503 without it). The signature covers the RFC 8785 canonical form of the whole document minus `signature` — if you add a field to the transcript, it is signed automatically, but a value that isn't JSON-canonicalizable (a `Date`, `undefined` inside an array, a non-finite number) will throw, so convert first. `key_id` is derived from the public key, never configured; rotated keys go in `TRANSCRIPT_RETIRED_PUBLIC_KEYS` so old transcripts keep verifying. `POST /api/transcript/verify` and `GET /api/transcript/keys` are public. Import requires the transcript's `student.email_hash` to match the caller's email (a valid signature proves we issued it, not who is uploading it), carries over only final decisions (`approved`/`rejected`; pending becomes `none`), and dedupes on `logs.import_source_id` — unique per account — so overlapping transcripts can't double-count hours. `logs.import_attestation` keeps the signed claims a log arrived with; the logs PATCH clears it whenever it resets verification. Proof files are never in a transcript — only whether one exists and who retains it.

- **Tenant requirements** (`server/requirements.js`, `server/policy.js`, `server/routes/requirements.js`, editor `src/components/RequirementsSettings.jsx`): a school — or the org that owns it — defines how *its* students must log hours. Four sections (`logRules`, `customFields`, `goals`, `signIn`) stored as one JSONB `requirements` policy on `schools`/`organizations`. Inheritance is **per section, not per field**: a section absent from a school's JSON means "inherit", resolved school → org → defaults by `resolvePolicy()`, which also reports the source per section so the UI can say where a rule came from. **Every default is fully permissive** — adding a rule must change nothing for a tenant that configured nothing, so the server's defaults preserve the old API behavior while `formFieldRequirements()` in `src/lib/requirements.js` keeps the Log Hours form's own long-standing required fields (location/supervisor/proof) until a tenant defines `logRules`. `server/requirements.js` is pure and is imported by client code through the `@policy` alias (vite.config.js/jsconfig.json) so the form and `POST|PATCH /api/logs` apply *one* validator — never fork it. Custom-field answers land in `logs.custom_fields`, filtered by `sanitizeCustomFieldValues()` so only declared keys are stored. `signIn.ssoOnly` is enforced in `POST /api/auth/login` **after** the password verify (so it isn't an oracle for which addresses belong to a school) and **only for `role = 'student'`** — a school admin shares the school_id and would otherwise lock itself out of the toggle; `signIn.allowedEmailDomains` is enforced at `POST /api/school/join`, never at login, so adding it later can't lock out the existing roster. Changes are audited as `requirements.changed`.
- **Live-site test robot** (`scripts/live-check.mjs`, `.github/workflows/live-check.yml` every 6 hours, `POST`/`GET /api/status/live-checks`, `live_check_runs` table, `LiveChecksCard` in Admin → Incidents, #315): headless Chrome checks the deployed site (backend + email health, security headers, key API routes answering without 404/5xx, public pages loading with no script errors or CSP violations, the Turnstile widget, and the map/Google Form sources under the CSP) and posts the results with `x-cron-key: CRON_SECRET`. The backend emails `ADMIN_EMAIL` when a check's failure streak reaches `LIVE_CHECK_FAILURES_BEFORE_ALERT` (2) and again when it passes, and keeps the last 200 runs. The raw results are admin-only; what reaches the public `/status` incidents (#324, `syncLiveCheckIncidents()`) is one plain-language incident per user-facing service — Backend API, Sign-in, Website pages, App pages, Maps & forms (`publicServiceFor()` / `PUBLIC_LIVE_SERVICES`) — opened when a check reaches the alert threshold and resolved when that service's checks all pass. Security headers, email (the /health probe owns "Email") and `TEST …` checks never go public; subscribers are notified, the admin isn't emailed twice, and no GitHub issue is filed. Keep those service names distinct from the /health ones ("Database", "Email") so the robot never resolves an incident it didn't open. The Actions run is red only if the report couldn't be delivered, so failing checks don't also trip the CI-failure routines. It never completes a sign-up. **Signed-in checks and AI summary (#318):** with `MONITOR_EMAIL`/`MONITOR_PASSWORD`/`MONITOR_SECRET` (same values on Render and as GitHub secrets) `seedMonitor()` in `server/monitor.js` keeps an empty student account ("Live Check Robot", must be `@test.com`, never takes over an existing account), and `turnstileUnlessMonitor()` lets `POST /api/auth/login` skip the CAPTCHA only when `x-monitor-key` matches `MONITOR_SECRET` *and* the email is `MONITOR_EMAIL` — keep that pair-check if you touch it, or the key becomes a CAPTCHA bypass for every account. The robot then loads the signed-in pages read-only and runs the real Log Hours search → pick → map flow. With `OPENROUTER_API_KEY` (default model `openrouter/free`, which routes to whichever free model is up) or else `ANTHROPIC_API_KEY` (Claude Haiku) a failing run gets a 2–4 sentence summary (`live_check_runs.summary`); repo variable `LIVE_CHECK_MODEL` overrides the model. It is shown in the alert email and the card, labelled as AI-written. Add a check when a release adds a page or third-party source the CSP must allow.
- **Sync PIN expiry** (`POST /api/auth/sync-login`, `PUT /api/auth/sync-pin`, `POST /api/auth/sync-pin-auth`, Settings → sync PIN, #313): the 5-digit sync PIN is the whole credential for `sync-login`, so it lasts `SYNC_PIN_TTL_MINUTES` (15) from `users.sync_pin_expires_at` and is cleared when used (the clearing `UPDATE` is the atomic spend). `sync-login` only matches an unexpired PIN; a PIN with no expiry predates this and counts as expired. `clearExpiredSyncPins()` runs before each uniqueness check so dead PINs don't hold numbers. `publicUser()` hides an expired PIN and sends `syncPinExpiresAt`, which Settings counts down; Settings generates the PIN with `crypto.getRandomValues`.
- **Sign-up email code** (`POST /api/auth/register/send-code`, `signup_codes` table, `sendSignupCodeEmail()` in `server/email.js`, the "Check your email" step in `src/pages/Register.jsx`, #310): a student, Volunteer Task Maker or parent sign-up is checked in full by `readSignup()` (shared with `/register`), then a 6-digit code is emailed and only `POST /api/auth/register` with a matching `emailCode` creates the account. The code is bcrypt-hashed, lasts 10 minutes, dies after 5 wrong tries, and is deleted when spent; a new one can be sent once a minute per address (the `WHERE` on the upsert), and only the newest works. With no email provider outside production the code is printed to the server log instead. The CAPTCHA lives on send-code, so the code screen shows a fresh widget for "Send a new code".
- **Under-13 parental consent** (`POST /api/auth/register`, `server/routes/parentConsent.js` at `/api/auth/parent-consent` — mounted ahead of `/api/auth` — `sendParentConsentEmail()` in `server/email.js`, the age question in `src/pages/Register.jsx`): a student who self-registers and says they are under 13 must give a parent or guardian's email. The account is created with `parental_consent_status = 'pending'`, **no session is issued and no welcome email is sent**, and the parent is mailed a backend link whose 64-hex token is the credential. The GET only renders Approve / Decline and the POSTs change state, so a mail scanner can't approve a child's account. Approve unlocks it (`parental_consent_at`); decline deletes it, but only while still pending. `POST /api/auth/login` refuses a pending account *after* the password verify and re-sends the parent email at most once an hour; pending accounts older than `PARENT_CONSENT_TTL_DAYS` (14) are deleted opportunistically on the next registration, since there is no job runner. `parental_consent_status` is `NULL` for everyone the step doesn't apply to — 13+, and students a school added or that arrived through SSO, whose consent the school carries — so never treat `NULL` as unapproved. Any new route that issues a session from a password must apply the same pending check. The wording lives in three places that must agree: `Privacy.jsx`, the parent email, and `docs/STORE_LISTING.md`.
- **Join offer** (`server/promo.js`, `GET|PATCH /api/settings/promo`, editor in the admin Settings tab, banner `src/components/PromoBanner.jsx`, rendered **only in the landing-page hero** — not on the signup pages, whose visitors have already decided, and not on customer dashboards, where an already-invoiced school would be shown a first-invoice discount it can't claim; dashboards carry only the referral card): one admin-defined discount at a time ("10% off your first month"), stored as a single `promo_offer` row in `site_settings`. `server/promo.js` is pure and is imported by client code through the `@promo` alias (vite.config.js/jsconfig.json) — the banner and the admin's invoice preview quote a price and `POST /api/invoices/admin` is what actually charges it, so both run the same `applyPromoAmount()`; never fork it. The client sends `applyPromo: true`, never an amount off: the server re-resolves the current offer and re-runs `promoAppliesTo()` before billing, so a stale admin tab can't apply an offer that has since been edited or ended. `invoices.amount` stays what is owed (every existing reader — the paid/unpaid gate, the emails, `payment_events` — is untouched); `subtotal`/`discount_percent`/`discount_label` are **frozen onto the row** rather than read back from `site_settings`, so editing the offer can never restate an invoice already sent. An offer may carry a `code` (uppercased on save, printed on the banner to quote) and a `maxRedemptions` cap — a cap requires a code, because **`invoices.discount_code` *is* the redemption ledger**: uses are a `COUNT` over non-void invoices carrying it, so voiding a mistaken invoice hands the use back and there is no second counter to drift. `countPromoRedemptions()` fails closed (an errored count reads as fully claimed, never as unlimited). `GET /api/settings/promo` is public, strips `enabled`, and returns `null` for a fully-claimed or `invite`-only offer so the banner can't promise a discount nobody can still get. It **never publishes usage** — no `remaining`, `redemptionsUsed` or `maxRedemptions`, and no "N left" on the banner: that is pressure we don't put on customers, and on an unauthenticated endpoint it leaks how a campaign is going. The counts are admin-only (`GET /api/settings/promo/admin`, the editor's usage line, the invoice modal). The cap is checked per request, not locked — two admins invoicing at the same instant could both pass, which is acceptable for an admin-only action but is why the cap is a marketing limit, not an accounting control. The contact form's optional coupon field (`contact_messages.coupon_code`) is a hint for the admin and **never blocks a message**, unlike the account-ID field next to it.
- **Referrals** (`server/routes/referral.js`, card `src/components/ReferralCard.jsx`): the join offer gains `visibility` (`public` | `invite`) and a `referral` flag. `publicPromo()` returns null for an `invite` offer, so it never reaches the landing page, signup pages or About — it is mailed to existing customers to pass on, and their own dashboard card is where they read the terms. Every school/org gets an immutable `referral_code` (`generateReferralCode()`, backfilled on boot like `account_code`); a new school quotes it at registration, which writes a `referrals` row — **a bad code never fails the registration**, it just attaches nothing. Lifecycle is `pending` → `earned` (the referred customer has been invoiced, so the reward is real — `markReferralEarned()` fires from `POST /api/invoices/admin`) → `redeemed` (spent on the referrer's own invoice); `percent_off` is frozen on the row for the same reason invoices freeze theirs. An invoice carries the join offer **or** one referral credit, never both compounded, and the credit is re-resolved server-side from `earnedCredits()` rather than trusted from the request, so a stale tab can't spend somebody else's. `POST /api/referral/admin/send-invites` mails each customer **separately** (one message per recipient — a shared thread would disclose the customer list) via the standard automated-email footer, is two-step (`dryRun` powers the admin's confirm dialog), records `referral_invite_sends` so a second click skips anyone already contacted unless `force`, and takes `only: ["school:<id>"]` for a test send. Voiding a referral is allowed only while `pending`/`earned` — a redeemed one backs a real invoice.
- **Registration codes** (`server/registrationCodes.js`, `server/routes/registrationCodes.js` at `/api/registration-codes`, panel `src/components/RegistrationCodesPanel.jsx` in the admin Invites tab, field `src/components/RegistrationCodeField.jsx`, #287): a paid school or an organization can register **only** with an invite link or a one-time 16-character code (a free club needs neither, see *Free club plan*) the admin generated (`generateRegistrationCode()`, grouped `XXXX-XXXX-XXXX-XXXX`), so nobody becomes a customer without contacting us. Students, volunteers and parents are not gated. Only a SHA-256 hash and the last four characters are stored — the plaintext leaves the server once, in the create response, and the panel's reveal dialog is the only place it's shown. `claimCode()` spends a code in a single conditional `UPDATE … RETURNING` so two sign-ups can't share one, and the register routes call it **after** every other check (email/school code taken), so a typo doesn't cost the customer their code; if the account insert then fails, `releaseCode()` hands it back. Input ignores case, spaces and dashes. An invite link still works on its own — it is the same kind of one-time, us-issued credential, and an organization's own school invites keep working.
- **Free club plan** (`server/plans.js`, `schools.plan` = `club` | `school`, #506): a club is free for one adviser and up to `CLUB_STUDENT_LIMIT` (50) students with every school feature. `POST /api/school/register` with `plan: 'club'` needs **no registration code** (Turnstile still applies); an invite link always makes a `school`. A club is never payment-locked: gate with `schoolIsActive(row)` (needs `plan` + `payment_status`), never `payment_status === 'paid'` alone, and the client reads `user.schoolPlan`. Every write that puts a student into a school — `/school/join`, transfer accept, school-invite accept, SSO just-in-time sign-up — goes through `joinWithSeat(schoolId, write)`, which locks the school row and re-counts, so simultaneous joins can't overrun 50; `clubSeatProblem()` is only an early, friendly check. A new join path must use `joinWithSeat`. A club gets at most `CLUB_MAX_CO_ADMINS` (1) co-adviser, and an admin can't make a school with more than 50 students a club. `/school/info` gives the school's own admins `plan`, `studentCount` and `studentLimit` (`ClubPlanCard` on the Students tab). The admin switches plans in Admin → Schools (`PATCH /api/school/admin/:id/plan`); moving a club to `school` makes the payment lock apply, so invoice it first.
- **Announcements** (`server/routes/announcements.js` at `/api/announcements`, `announcementHtml()` in `server/email.js`, composer `src/components/AnnouncementComposer.jsx` opened from the admin Schools, Organizations and Users tabs, banner `src/components/AnnouncementBanner.jsx`, #290): admin notices like planned downtime, **separate from `admin_notifications`**, which are payment notices with bank details. Each picks any of five audiences — `to_schools`, `to_orgs`, `to_students`, `to_parents`, `to_volunteers` (at least one) — and shows as a banner on that audience's dashboard (school admins/staff incl. the payment-locked view, the org dashboard, the student/volunteer `Dashboard.jsx`, `ParentDashboard.jsx`) until `show_until` (1 hour to 30 days) or until the admin ends it (`ended_at`). `GET /announcements/mine` maps the **token's** role to its column, never anything in the request. Each recipient is emailed once, **one message per address** (school/org contacts plus matching `users`, deduplicated by lowercased email, never a shared thread); an under-13 account still pending parental consent and the `@test.com` fixtures are skipped. Sending happens **after** the 201 response, five at a time, bumping `emails_sent` toward `emails_total` — a large audience must not hold the admin's request open or hit the provider all at once, and a failed send is simply not counted. Banners are dismissible per device (`voluntrack:dismissed-announcements`); a local-only account (no token) never sees them. **An organization's own announcements** (#557, `POST|GET /api/announcements/org`, `POST /org/:id/end`, the org dashboard's Announcements tab, `OrgAnnouncementsCard`): rows with `organization_id` set, to its schools' admins/co-admins (`to_schools`) and/or their students (`to_students`), emailed to those people and each school's `contact_email` with the org's name in the subject; `/mine` shows them only to accounts whose school belongs to that org, with `from` = the org's name for the banner. Five a day per org. The admin's list and end route ignore org rows, and an org can end only its own.
- **Passkeys and app lock** (`server/passkeys.js`, `server/routes/passkeys.js` at `/api/auth/passkey` — mounted ahead of `/api/auth` — `src/lib/passkey.js`, `src/components/PasskeySettings.jsx`; `src/lib/appSession.js`, `src/components/AppLock.jsx`): a passkey is a **second factor**, not passwordless sign-in — `POST /api/auth/login` answers a correct password with `requiresTotp: true` (kept true for any second factor so older clients still stop at a 2FA step), a `tempToken`, and `methods` (`totp`, `passkey`); the client then runs `/challenge/options` + `/challenge/verify`. Only public keys are stored (`passkeys`); challenges live in `webauthn_challenges` and are deleted when checked, pass or fail, because passkeys often report a signature counter of 0 so the counter can't catch a replay. - **Keeping the backend awake** (`server/keepAwake.js`, `GET /api/status/ping`): Render's free tier spins the service down after ~15 min with no inbound traffic, and a cold boot outruns the 5s timeout in `src/lib/status.js` — so `/status` paints a sleeping-but-healthy backend as "Backend API — unreachable". `keep-warm.yml` cannot prevent this: GitHub throttles `schedule:` crons hard, so its `*/10 * * * *` actually fires every 2-5 hours. The backend therefore self-pings its own public origin every 5 min (out and back through Render's load balancer, which is what resets the idle timer), gated on `KEEP_AWAKE=1` so only the deployed service does it. It pings `/ping` and **not** `/health` on purpose: `/health` opens a Database incident on a single failed `SELECT 1` with no failure threshold, and every incident emails the admin and all subscribers, so polling it on a timer would turn one transient Neon blip into a broadcast. This can't recover a service that already fell asleep (nothing is running to send the ping), which is why `keep-warm.yml` stays on as the outside-in monitor. Budget: ~730 h/month against the free tier's 750.
