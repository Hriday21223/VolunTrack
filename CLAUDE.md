# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev       # Vite dev server at http://localhost:5173 (client-only, localStorage mode)
npm run backend   # Express API at http://localhost:10000 (server.js) — Vite proxies /api to it in dev
npm run build     # prebuild runs scripts/generate-seo-files.mjs, then vite build to /dist
npm run preview   # preview the production build
npm run lint      # eslint .
```

There is no test suite; CI (`.github/workflows/ci.yml`) only runs `npm run lint` and `npm run build` on push/PR to `main`.

To run the full backend locally, copy `.env.example` to `.env` and set `DATABASE_URL` (Postgres), `JWT_SECRET`, and optionally `APP_ENCRYPTION_KEY` (only needed to configure school SSO — those endpoints return 503 without it) plus SMTP vars (`EMAIL_HOST`/`EMAIL_PORT`/`EMAIL_USER`/`EMAIL_PASSWORD`) — without SMTP config, recovery codes are shown in the UI instead of emailed. Without `DATABASE_URL`, the backend runs in email-only mode (no accounts API).

## Architecture

This app has two parallel, loosely-coupled data layers, and most nontrivial changes touch the boundary between them:

1. **Client-only mode (default)**: all state lives in `localStorage` under the `voluntrack:` namespace (`voluntrack:user`, `voluntrack:logs`, `voluntrack:goals`, `voluntrack:achievements`, `voluntrack:theme`). `src/api/index.js` is the data-access layer over localStorage; `src/lib/storage.js` defines the read/write rules and `src/lib/achievements.js` defines badge-earning logic. The app is fully usable with no backend running.
2. **Server-backed mode (optional)**: when `DATABASE_URL` is set, `server.js` boots a Postgres-backed Express API for accounts, school/organization dashboards, public volunteer tasks, and review moderation. `server/db.js` owns the schema and connection — beyond the core `users`/`schools`/`logs`/`goals` tables, it also covers `organizations` (multi-school orgs), `public_tasks`/`public_task_signups` (with attendance tracking), `supervisor_verifications` (hour-verification workflow), `parent_child_links`, `school_invites`/`organization_invites`, `contact_messages`, and `reviews` (moderation queue for the public testimonials on `About.jsx`); most migrations are additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements run on boot rather than a migration tool. `server/auth.js` handles JWT signing/verification and bcrypt password hashing; `server/routes/{auth,authSso,school,organization,logs,parent,contact,reviews,invoices,settings,status,storage}.js` are the route handlers (mount order is in `server.js` — `/api/auth/sso` must stay ahead of `/api/auth`); `server/ids.js` generates IDs/tokens.

`src/lib/logSync.js` bridges the two: logs authored locally can sync to the server side. When editing sync logic, check both the localStorage shape (`storage.js`) and the Postgres schema (`db.js`) stay compatible — this is not enforced by types.

Request-handling flow, middleware order, and the auth-gating pattern for `server/` are in `server/CLAUDE.md`.

### Roles

Seven roles gate routes and dashboards: `student`, `volunteer`, `parent`, `school`, `school_staff`, `org`, `admin` (see `users_role_check` constraints in `server/db.js` and `requireAuth(...)` calls in `server/routes/*.js`). `organizations` can own multiple `schools` (`schools.organization_id`); `org` accounts manage their schools' invites, `school`/`school_staff` manage their own students/staff, `parent` accounts link to student accounts via `parent_child_links`, and `admin` has cross-cutting access (school/org approval, payment status, review moderation, contact-message replies).

### Notable conventions

- Path alias `@` → `src/` (configured in `vite.config.js` and `jsconfig.json`).
- Dark mode is opt-in per device, persisted at `voluntrack:theme`.
- Drag-and-drop proof uploads are read via `FileReader` and stored as base64 in localStorage — keep proof files under ~1MB, since this inflates localStorage.
- Backend security posture (see `SECURITY.md`): rate limiting, input validation, parameterized Postgres queries via `pg`. Preserve parameterized queries when touching `server/db.js` or route handlers — no string-concatenated SQL.
- `server/turnstile.js` (`verifyTurnstile()` middleware) guards the public unauthenticated write endpoints (`POST /api/contact`, `POST /api/auth/register`, `POST /api/{school,organization}/register`) with Cloudflare Turnstile; the client widget is `src/components/Turnstile.jsx` (config in `src/lib/turnstile.js`). Both are no-ops unless `TURNSTILE_SECRET_KEY` / `VITE_TURNSTILE_SITE_KEY` are set — if you add the check to a new endpoint, wire the widget into its form in the same change so the two stay in sync.
- **School SSO** (`server/routes/authSso.js`): a school configures an OIDC connection to its own IdP (Google Workspace, Microsoft Entra, or generic OIDC) from the Sign-in tab of `SchoolDashboard`, and its students sign in there instead of with a VolunTrack password. The login page routes by email domain (`GET /api/auth/sso/discover`), the callback hands the SPA a single-use 60s code that `POST /api/auth/sso/exchange` trades for the normal app JWT — `signToken()` is reused, so nothing downstream of login is SSO-aware. Client secrets are AES-256-GCM encrypted via `server/secrets.js` (`APP_ENCRYPTION_KEY`); a connection may only provision accounts for a domain it has proven it controls (Google's `hd` / Entra's `tid` claim, or a DNS TXT record for generic OIDC), and enabling requires a passing test round trip plus a verified domain. `users.password_hash` is nullable because SSO users have none.
- **Audit trail** (`server/audit.js`, `server/routes/audit.js`): `audit_events` is an append-only record of *access* to student data, not just changes. Call `recordAudit(req, {...})` and **do not await it** — it is fire-and-forget by design, so a failed audit insert logs loudly but can never turn a legitimate read into a 500. Actions come from the `AUDIT` constant (a closed set, so a typo can't create a category nobody queries). Never put a credential in `meta` — notably not a presigned URL, which is itself a live grant. Nothing may UPDATE or DELETE a row except the retention prune (`POST /api/audit/internal/prune`, `x-cron-key` vs `CRON_SECRET`, driven by `.github/workflows/audit-prune.yml`), which deletes by age alone; the window is `AUDIT_RETENTION_DAYS` (default 400). Actor FKs are `ON DELETE SET NULL` so deleting an account can't erase what it did — `actor_role` and `actor_hash` survive, keeping events attributable without retaining the identity. Any new route that reads a student's documents or roster must record an event. See #146.
- **Tenant storage** (`server/routes/storage.js`, `server/storage/s3.js`): a school or org attaches its own S3-compatible bucket (`tenant_storage`) so proof-of-service files upload straight from the student's browser to *their* bucket — VolunTrack stores a pointer, never the bytes, so we don't hold minors' documents. Credentials are AES-256-GCM encrypted via `server/secrets.js`, so these endpoints return 503 without `APP_ENCRYPTION_KEY` (same posture as SSO). A config only reaches `status='active'` after `POST /api/storage/test` completes a real put/get/delete round trip, mirroring the SSO "must pass a test before enabling" gate. `server/storage/s3.js` is a hand-rolled SigV4 *query* presigner (no AWS SDK) verified against AWS's published test vector — if you touch the signing math, re-check it against that vector. The tenant-supplied `endpoint` is fetched by our server during a test, so `assertSafeEndpoint()` guards SSRF (https only, no IP literals, no internal names) — keep that check if you add providers. Uploads go browser → bucket via `POST /api/storage/upload-url`: the server picks the object key (never the client's filename) under `students/<userId>/`, and signs `content-length` so an upload is pinned to the size it declared. `logs.proof_storage_id`/`proof_key` are the pointer; `proof_storage_id` is recorded per file rather than resolved from the student's school at read time, so a transfer or bucket rotation can't orphan history. When a log claims a `proofKey`, `keyBelongsTo()` re-verifies it sits in that student's own namespace — never trust a caller-supplied key. `GET /api/storage/download-url/:logId` is the audited moment (`proof.download_url_minted`): after it, the URL works for whoever holds it. See #143.

- `scripts/generate-seo-files.mjs` runs as `prebuild` and generates SEO-related static files consumed by `index.html` (`%VITE_SITE_URL%` placeholders) — `scripts/site-url.mjs` resolves the site URL from env for both this script and `vite.config.js`. **It rewrites tracked files** (`public/robots.txt`, `public/sitemap.xml`, `public/llms.txt`), and falls back to `http://localhost:5173` when `VITE_SITE_URL` is unset — so a plain local `npm run build` leaves those three dirty with localhost URLs. Never commit that: it would point the production sitemap and robots.txt at localhost. Either run builds with `VITE_SITE_URL` set to the real origin, or `git checkout --` those three files afterwards.
- Deployment targets: Render (`render.yaml`) for the backend, Netlify (`netlify.toml`), Vercel (`vercel.json`), or Cloudflare Workers Static Assets (`wrangler.jsonc`) for the frontend — see `DEPLOYMENT.md` for details.
- Scheduled work runs from GitHub Actions (`.github/workflows/*.yml` `schedule:` cron), not on Render (its free tier has no cron and sleeps when idle) — a workflow either runs a `scripts/*.mjs` (e.g. `notify-daily-scan.mjs`) or `curl`s a backend endpoint (e.g. `keep-warm.yml`). The **parent weekly progress digest** does the latter: `server/digest.js` builds/renders/sends; `POST /api/parent/internal/run-weekly-digest` (guarded by an `x-cron-key` header vs. `CRON_SECRET`) is hit weekly by `parent-weekly-digest.yml`; `POST /api/parent/admin/send-weekly-digest` is the admin/testing trigger (`{ weekStart?, parentId?, force?, dryRun? }`). Idempotency: `parent_digest_sends (parent_id, week_start)`. Opt-out: `users.weekly_digest_opt_out` + `users.digest_unsub_token`, public two-step `GET` (confirm page) + `POST` `/api/parent/digest/unsubscribe/:token` (the state change is on the POST so mail scanners can't opt a parent out).
